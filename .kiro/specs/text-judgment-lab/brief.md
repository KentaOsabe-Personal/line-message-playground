# Brief: text-judgment-lab

## Problem

本人が自身のiPhone・LINEアカウントで、チャットUI、JevのChoice・Score・Noulによる文章判定、判定に応じた会話分岐を学びたい。既存の管理・配信機能には、自由文と選択肢で相談しながら発言ごとの判定を観察する場がない。

個人検証の目的を満たす中で、考慮事項と実装量が最も少ない方法を優先する。

## Current State

- 既存のReact・TypeScript・React Router・Tailwind CSS、LIFF SDK、Django・DRF・HTTPX、Compose・ngrokを利用できる。
- `/liff`配下は既存のowner認証と4つの管理機能の画面である。既存のLINEログインAPIはowner sessionを発行するため、ラボのログインにそのまま利用すると利用権限と管理権限を分けられない。
- 文章判定ラボ、Jev接続、開発用ミニアプリ専用の入口・認証は未実装である。
- 正式Specの入力は[文章判定ラボ 要件整理](../../../TEXT_JUDGMENT_LAB_REQUIREMENTS.md)とする。[用語集](../../../CONTEXT.md)の確定用語を使い、[開発案](../../../TEXT_JUDGMENT_LAB_PLAN.md)の古い会話例や未確定候補で承認済み要件を上書きしない。
- 要件整理資料は正式なRequirements・Design・Tasks・Implementationの承認を兼ねない。

## Desired Outcome

本人だけが開発用LINEミニアプリを開き、「通知が届かない」「通知の設定方法を知りたい」の2種類を、入力から質問、iPhone向け案内、本人の結果回答まで進められる。自由文の言い換え・否定・曖昧な回答を少数試し、判定結果と会話の違いを確認できる。

Choiceで分類、Scoreで支障に応じた追加質問、Noulで急ぎに応じた表示変更を観察できればよい。判定精度の数値目標や全文章への正答は完成条件にしない。

## Approach

**採用: A案・画面側で会話を進める。** 2026年9月19日に、ユーザーが単一Specの方針と本方式を選択した。

同じReactアプリに既存管理画面とは独立した入口を追加する。純粋な状態遷移で会話・確定回答・確認回数・終了状態を管理し、会話と判定詳細は画面のメモリだけに保持する。選択肢回答は通信なしで処理する。

同じDjangoにラボ用の認証・認可とJev判定APIを追加する。サーバーが本人確認、入力・文脈の検証、固定した判定質問の組み立て、Jev接続、応答の検証・正規化を担う。既存HTTPXを使い、新しいAI SDKや会話管理基盤を前提にしない。

会話状態やAIの判定を認証・認可に使わない。Jevの各質問は同じ文脈に対する独立判定として扱い、判定間の整合と会話への適用はコードで決める。

**比較したB案:** 文脈を毎回Djangoへ送り、選択肢回答を含む会話進行をサーバーで決める。Pythonへルールを集約できるが、選択肢にも通信と失敗処理が必要になる。今回の画面内だけの個人検証ではA案の方が実装量を抑えやすいため採用しない。

## Scope

- **In**: 本人向け開発用ミニアプリ入口と権限分離、自由文・最初の例文・追加質問の選択肢、2種類の通知相談、Jevの3判定、未回答項目の読み取りと質問省略、判定要確認時の確認、対象外・複数相談・訂正希望への対応、iPhone向け固定案内と公式ヘルプ、結果確認、終了・中断・やり直し、判定詳細、通信制御、代表例の自動統合検証。
- **Out**: Android向け案内、他のテスターへの提供、一般公開・審査公開、自由な回答文生成・別の生成AI、画像・音声、LINEトークへの通知、履歴保存・一覧・分析・復元、部分訂正・巻き戻し・相談の自動切替、複数画面同期、端末設定や通知到達の自動検知、大量評価・精度目標、新たな汎用認証基盤。

### 維持する会話・表示契約

- 自由文と最初の例文ではChoice・Score・Noulを使う。追加質問の選択肢は回答を確定し、Jevを呼ばない。判定条件・質問数・文脈の具体形は設計で決める。
- 確認順は相談の種類、通知の範囲、必要な回避策、曖昧な場合の急ぎ、案内とする。明確に読み取れた未回答項目だけを補い、確定済み回答を上書きしない。
- Scoreは0〜2の3段階の支障を扱う。「通知が届かない」で支障が大きい、または判定要確認の場合だけ、LINEを開けばメッセージを確認できるかを追加確認する。確認できない場合は急ぎの追加質問をせず、公式ヘルプへ案内して未解決終了にする。
- 「設定方法」の相談にはScoreによる回避策の質問を入れない。範囲に応じて全体または特定トークの案内を選ぶ。
- 急ぎなら要点を1〜2文で先に示し、詳しい手順は開いて読めるようにする。急ぎでなければ手順を最初から表示する。
- 判定要確認は本人の「分からない」や通信失敗とは区別する。自由文による確認でも読み取れなければ、その質問だけ選択肢回答とし、次の質問で自由入力を再開する。
- 対象外や複数相談の扱いは要件整理第6節に従う。確定済み回答を変更せず、必要なら終了して新しい相談を始める導線を示す。
- 解決・設定完了・未解決終了・中断を区別する。「まだ試していない・確認できない」は終了せず、案内と回答欄を残す。
- 終了・中断後も表示を残す。新しい相談では前の表示と文脈を消し、再読み込み・開き直しでは復元しない。
- 判定中は追加送信を止めるが、中断と新規相談は可能にする。中断・タイムアウト後の結果をどの相談にも反映しない。
- 通信失敗や不完全な判定は会話を進めず、通常の入力欄から送り直せるようにする。自動再試行、専用再試行ボタン、部分結果での継続は追加しない。
- 発言ごとの「判定の詳細」は初期状態で閉じ、分類・点数・確率・判定時間を観察できるようにする。

## Boundary Candidates

1. **入口・本人確認・権限分離**: ラボ専用LIFF設定、検証対象チャネル、本人許可、API認可、認証期限と復帰。管理用sessionを発行しない。
2. **判定境界**: 文脈・入力検証、Jev質問、HTTPX gateway、応答正規化、時間計測、通信失敗。会話履歴をサーバーへ保存しない。
3. **会話状態遷移**: 確定回答、未回答項目、質問順、確認回数、対象外・複数相談、終了とやり直し、遅延結果の不採用。
4. **画面・案内・観察**: チャット操作、iPhone向け手順、結果確認、判定詳細、入力待ち、ページ内の表示寿命。
5. **統合・検証**: 境界DTO、認証分離、相談分岐、失敗・中断、既存画面への回帰、代表例の自動統合検証。

## Out of Boundary

- 既存owner session、本人連携、全連携解除、管理・配信APIの契約を変更しない。ラボの認証結果を既存管理APIの許可根拠にしない。
- 既存4機能の管理ナビゲーションにラボを組み込むことは前提にしない。独立入口の追加を本Specが所有する。
- ラボ用のミニアプリ設定をMessaging APIチャネル管理機能へ取り込まない。
- 会話管理のためのDBモデル、永続storage、queue・workerは追加しない。認証の保持方式は設計で最小案を選ぶ。

## Upstream / Downstream

- **Upstream**: `app-screen-separation`の既存React構成・共通スタイル、`line-account-linking`の本人検証と秘密情報保護の原則、Compose・ngrokのHTTPS経路。既存owner認証は隣接する保護対象であり、ラボへの管理権限付与には再利用しない。
- **外部準備**: 開発用LINEミニアプリのLIFF ID・チャネル設定と本人のアクセス権、JevのAPIキー・利用可能なアカウント。設定値の取得や実機での成立確認は未実施。
- **Downstream**: 本SpecのRequirements・Design・Tasks・Implementation。ユーザーによる任意の実機確認、公開、多人数利用、履歴分析等は今回の完成条件に含めない。

## Existing Spec Touchpoints

- **Extends**: なし。既存Specを再オープンせず、独立入口・ラボ認証・判定・会話を新規Specで所有する。
- **Adjacent**: `line-account-linking`のowner権限・session寿命、`app-screen-separation`の`/liff`・復帰先・404、`line-channel-foundation`のMessaging API設定。新規route配線と既存画面の回帰確認は本Specの統合作業とする。
- 既存Spec・ロードマップ・用語集の古い記述に差がある場合は、今回の対象と関係する現行要件・実装を照合し、ラボ追加を理由に過去の仕様全体を修正しない。

## Spec Size Assessment

- **Verdict**: PASS (single-spec)
- **Projected executable tasks**: 36〜39件。方式選択・コード探索・技術適合確認後に再評価した。1件1〜3時間とし、各領域の単体テストに加え、統合・自動回帰を含む。会話の永続化・移行は不要で、認証保持に伴う移行が必要になれば設計時に加算して再判定する。
- **Independent responsibility seams**: 5（入口・本人確認、判定境界、会話状態遷移、画面・案内・観察、統合・検証）。独立して提供する成果は「本人が相談と判定を観察するラボ」の1つ。
- **外部・状態ワークフロー**: 外部連携はLINE本人検証とJev判定の2系統。会話は画面内の1つの状態遷移であり、外部資源作成・配信・補償処理を持たない。

| 作業範囲 | 実行可能タスク見込み |
| --- | --- |
| ミニアプリ入口・本人確認・権限分離 | 5〜6 |
| Jev接続・判定契約・通信制御 | 5〜7 |
| 会話分岐・回答確定・終了状態 | 8〜10 |
| チャットUI・案内・判定詳細 | 6〜8 |
| 統合・認証・失敗時テスト・自動回帰 | 6〜7 |

- **依存順**: 入口・認証と判定DTOの契約を定義 → 判定adapterと純粋な会話遷移を実装 → 画面へ接続 → 統合・自動回帰。具体的なファイル所有とtask graphはDesign・Tasksで確定する。
- **検証境界**: Backendは未認証・本人不一致・誤チャネル・不完全応答・通信失敗を検証する。Frontendは各相談、確定回答の維持、選択肢限定、中断後・タイムアウト後の遅延結果、新規相談への混入防止を検証する。既存のowner認証・routeに回帰がないことを確認する。
- **Rationale**: review attention帯だが、各責務は一つの利用者成果へ収束する。独立rolloutや複数の補償状態機械、履歴移行がなく、内部契約と依存順を固定できる。Requirements・Design・Tasksで再判定し、40件以上またはbounded reviewが構造的に収束しない場合は分割へ戻る。単一Specの例外承認として扱わない。

## Constraints

- 文書は日本語とし、既存の技術構成・命名・責務分離・テスト慣習を使う。
- 実機確認の実施や機種・iOS・LINEバージョンの記録はユーザーが任意で行い、本Specの機能・タスク・完成条件に含めない。基本テストは既存Vitest・jsdom・Django test runnerで行う。
- 自由文には架空の相談を使い、JevのAPIキーとLINE本人証明の検証をサーバーに閉じ込める。入力本文・秘密値を不用意にURL、永続storage、ログへ残さない。
- LINEの開発用内部チャネルに対応したLIFF ID・検証対象チャネルを使う。既存管理チャネルのaudience検証を緩めない。本人許可はサーバーが検証した識別情報で判断し、表示名等のプロフィール取得を必須にしない。
- 会話を消す契機と認証が失効する契機を分ける。認証方式、復帰時の扱い、入力長、制限、timeout秒数、モデル、質問文、境界値、数値表示・時間測定区間は要件整理第11節に従い設計で決める。

### 技術適合確認と未検証事項

2026年9月19日にコード探索と公式資料の確認を実施した。採用方式を変更する阻害要因は確認していない。実Jev呼出、本人のConsole設定、iPhone試験、全依存の脆弱性監査は行っていない。

- [TypeSafe HTTP API](https://docs.typesafe.ai/api)と[Quick start](https://docs.typesafe.ai/introduction/quickstart)により、既存HTTPXで接続でき、新規SDKを前提にしない。質問単位の部分エラー形式は未確認のため、必須結果の欠落・型不一致・不正数値は判定失敗へ収束させる。
- [Jevの質問モデル](https://docs.typesafe.ai/introduction)は同一文脈への独立判定である。[Models](https://docs.typesafe.ai/models)の日本語に関する制約を踏まえ、言い換え・否定・曖昧な代表例で確認する。精度保証や大量評価へ拡張しない。
- [ミニアプリのConsoleガイド](https://developers.line.biz/ja/docs/line-mini-app/discover/console-guide/)、[ID token検証](https://developers.line.biz/en/reference/line-login/#verify-id-token)、[認可フロー](https://developers.line.biz/en/docs/line-mini-app/develop/channel-consent-simplification/)に基づき、開発用IDの組、本人のアクセス権、プロフィール非依存の本人確認を設計する。
- 主要技術の保守終了や追加GPL依存は確認していない。HTTPXはBSD、ReactはMITで、LIFFには既存のLINE利用条件が適用される。新規ライブラリが必要になった場合は改めて互換性を確認する。
- 調査では既存Django 6.0.7に対する[6.0.8のセキュリティ修正](https://docs.djangoproject.com/en/6.0/releases/6.0.8/)を確認した。既存基盤の保守事項として設計開始時に現状を確認する。Discoveryで依存更新や実装は行わない。
