# 文章判定ラボ 要件整理

> この資料は旧仕様の検討記録です。2026年10月4日に、自由文の「分類・感情・急ぎの要望」を表示するシンプルなチャットへ方針を変更しました。現行仕様は[文章判定ラボの要件](../../.kiro/specs/text-judgment-lab/requirements.md)を参照してください。以下の本文は当時の記録として残しています。

更新日：2026年9月19日

## 1. 目的と進め方

本人のiPhone・LINEアカウントで、チャットUI、Jevの文章判定、判定による会話分岐を学ぶ。**個人検証の目的を満たす中で、考慮事項と実装量が最も少ない方法を優先する。**

本書は正式なSpecを作る前の要件整理資料であり、設計・タスク作成・実装の承認を兼ねない。一問ずつ回答を待って合意した内容を整理した。確定した用語は[CONTEXT.md](CONTEXT.md)に残している。

## 2. 作る範囲

- 本人だけがLINEミニアプリを開き、通知について相談できる。
- 扱う相談は「通知が届かない」「通知の設定方法を知りたい」の2種類。
- 自由入力、最初の例文ボタン、追加質問の選択肢を用意する。
- iPhone向けの実際に操作できる手順と、公式ヘルプへのリンクを用意する。
- Choice・Score・Noulを会話に反映し、発言ごとの判定結果をその場で確認できる。

実機確認は本人のiPhoneで行い、機種・iOS・LINEのバージョンを確認時に記録する。Android向けの案内、他のテスターへの提供、一般公開、通知音・プレビューなど細かな設定の網羅は含めない。

## 3. 基本の会話

### 通知が届かない

1. 通知が届かない範囲を「すべてのトーク／特定のトーク／分からない」で確認する。
2. Scoreで支障が大きい、または判断できない場合だけ、「LINEを開けばメッセージを確認できますか？」と聞く。
3. 範囲と回答に応じて、次の案内へ進む。

| 回答・状態 | 案内 |
| --- | --- |
| LINEを開いてもメッセージを確認できない | 公式ヘルプへの短い案内を表示し、未解決で終了 |
| 確認できる・分からない、または追加質問が不要 | 通知設定の確認手順へ進む |
| 設定の案内へ進み、範囲が「すべて・分からない」 | iPhoneとLINEアプリの通知設定 |
| 設定の案内へ進み、範囲が「特定のトーク」 | そのトークの通知設定 |

案内後、「解決した」なら解決として終了する。「まだ届かない」なら詳しい公式ヘルプを示し、未解決として終了する。

### 通知の設定方法を知りたい

1. 設定したい範囲を「全体／特定のトーク／分からない」で確認する。
2. 「全体・分からない」にはiPhoneとLINEアプリ全体、「特定のトーク」にはそのトークの通知をオン・オフにする手順を示す。
3. 「設定できた」なら完了する。「設定できない」なら公式ヘルプを示し、未解決として終了する。

この相談には、Scoreによる回避策の追加質問を入れない。

### 案内後の結果確認

解決・設定完了は本人の回答で判断し、端末の設定や通知の到達をアプリが自動確認することは求めない。

両方の相談に「まだ試していない・確認できない」を用意する。その場合は終了せず、同じ案内と回答欄を残す。結果が分かったら回答でき、その場で終えたい場合は「相談を終了する」で中断できる。

## 4. Jevの役割

| 判定 | 会話への反映 |
| --- | --- |
| Choice | 相談の種類や自由文の返答を分類し、次の質問・案内を選ぶ |
| Score | 支障の大きさを評価し、「通知が届かない」相談の追加質問に使う |
| Noul | 急いで対応してほしい要望の有無を判定し、案内の見せ方を変える |

Scoreの採点基準は次の3段階とする。例文は期待する意味を示し、実測結果ではない。

| 段階 | 意味 | 例 |
| --- | --- | --- |
| 0 | 支障なし | 通知の設定方法を知っておきたい |
| 1 | 不便だが、別の操作で目的を達成できる | 通知は来ないが、LINEを開けば読める |
| 2 | 必要な確認・操作ができず、目的を達成できない | 連絡を確認できず、待ち合わせ場所が分からない |

両方の相談で、急ぎの要望があれば案内の要点を1〜2文で先に表示し、「詳しい手順を見る」で操作手順を開ける。急ぎでなければ手順を最初から表示する。

## 5. 入力と確認のルール

- 自由文と最初の例文ボタンでは、相談の文脈を含めてChoice・Score・Noulを判定する。
- 追加質問の選択肢は、その回答を確定し、Jevを呼ばない。
- 入力から未回答項目の回答を明確に読み取れたら、同じ質問を省略する。不足・曖昧な項目だけを確認する。
- 確定済みの回答は新しい判定で上書きしない。変更したい場合は第6節のやり直しを使う。

例：「全部のトークで通知が来ません。LINEを開けば読めます。急いでいます」から必要な回答を読み取れた場合は、聞き直さず案内の要点へ進む。

### 判定が曖昧な場合

| 判定 | 確認方法 |
| --- | --- |
| Choiceで相談の種類・返答を分類できない | 今の質問に合う選択肢を示して確認 |
| Scoreで支障を判断できない | 「通知が届かない」相談だけ、回避策を追加確認 |
| Noulで急ぎか判断できない | 「お急ぎですか？」と確認 |

この「判定要確認」は、本人が「分からない」と回答した場合や通信失敗と区別する。最初の確認では自由文と選択肢を使える。自由文で答え直しても読み取れなければ、その質問だけ選択肢で答えてもらい、次の質問で自由入力を再開する。

確認は「扱う相談 → 通知の範囲 → 必要な回避策の確認 → 曖昧なら急ぎの確認 → 案内」の順で、一問ずつ進める。メッセージ自体を確認できないと分かった場合は、急ぎの追加確認をせず、公式ヘルプへ案内して終了する。

## 6. 話題変更・複数相談・対象外

| 入力 | 扱い |
| --- | --- |
| 別の相談へ変えたい・確定済みの回答を直したい | 「相談を終了する」→「新しい相談を始める」で最初から入力し直す |
| 複数の相談を含む | 先に扱うものを1つ選ぶ。もう一方を自動で続けない |
| 最初から対象外の相談 | 対応する2種類を伝え、入力例を示す |
| 相談途中に対象外の入力 | 対応範囲を伝え、現在の回答を保って直前の質問へ戻る |
| 対応内と対象外が混在 | 対応できない部分を伝え、対応する相談だけを扱う |

話題変更や訂正が必要だと読み取れた場合も、自動変更せず、やり直し操作を案内する。部分訂正、質問・案内の巻き戻し、切替専用の確認、発言の引継ぎは設けない。

複数相談から別の相談を選んだ場合もやり直しを案内し、現在の相談を選んだ場合は回答を維持する。対象外か判断できない場合は、第5節の確認へ進む。

## 7. 相談の終了と表示の保持

「相談を終了する」は、選択肢だけで回答する状態や判定中も使える。確認画面を挟まず「中断」とし、解決・設定完了・未解決終了と区別する。

| タイミング | 会話・判定結果の扱い |
| --- | --- |
| 終了・中断したとき | 表示を残して見返せる。回答・訂正は終了する |
| 新しい相談を始めるとき | 前の表示を消し、発言・回答・判定を持ち越さない |
| 再読み込み・閉じて開き直したとき | 復元せず、最初の入力から始める |
| 設定画面などへ一時的に移り、戻ったとき | ページが保持されていれば続行。再読み込みされたら最初から始める |

会話履歴の保存・一覧・分析、閉じた後の復元、確認を促す通知は作らない。

## 8. 判定待ち・失敗時の操作

- 判定中はその旨を表示し、自由文・例文・選択肢の追加送信を止める。過去の会話と判定結果は見られる。
- 判定中でも相談を中断し、新しい相談を始められる。中断後に届いた結果はどの相談にも反映しない。
- 判定に失敗したら「判定できませんでした」と表示し、会話を進めず、通常の入力欄から送り直せるようにする。
- 専用の再試行ボタン、自動再試行、一部の判定だけを使った継続、詳細なエラー分類画面は作らない。
- 通信タイムアウトを設け、失敗扱いにした呼出の遅延結果では会話を進めない。秒数は設計で決める。送信済みの外部処理そのものの停止は保証しない。

## 9. 判定結果の観察と完成条件

Jevで判定した発言ごとに、初期状態では閉じた「判定の詳細」を付ける。開くと、その発言の分類・点数・確率・判定時間を確認できる。

本人のiPhoneで少数の例を試し、次を確認できればよい。

1. 2種類の相談を入力から案内・結果確認まで進められる。
2. Choiceの分類、Scoreによる追加質問、Noulによる表示の違いを確認できる。
3. 言い換え・否定・曖昧な返答を試し、判定と会話の進み方を観察できる。

通常の開発上の動作確認は行う。判定精度の目標値、大量の評価データ、分析レポートは設けず、誤判定も観察対象とする。すべての文章を正しく判定することは完成条件にしない。

## 10. 開発案から引き継ぐ前提

[開発案](TEXT_JUDGMENT_LAB_PLAN.md)の次の前提を採用する。

- 既存のReact・LIFF SDK・Django・ngrokを活かし、開発用ミニアプリの入口と本人確認を用意する。
- Jevは文章を判定し、アプリは用意済みの質問・案内を選ぶ。別の生成AIや自由な回答文生成は追加しない。
- 入力には架空の相談を使う。Jevへの呼出とAPIキーの保持はサーバー側で行い、AI判定を認証・認可に使わない。
- ミニアプリを使えることと既存管理画面を操作できることを区別する。具体的な本人確認・権限の分け方は設計で決める。
- 画像・音声入力、LINEトークへの通知、本番公開は含めない。

## 11. 設計へ引き継ぐ事項

以下は新たな機能を増やさず、最小構成で設計時に決める。必要な仕様変更が分かった場合は、変更点を提示して確認する。

| 項目 | 設計で決める内容 |
| --- | --- |
| 判定条件 | モデル、質問文、渡す文脈、判定要確認の条件、Score・Noulの境界値。確定済み回答を守り、矛盾する判定で勝手に進めない |
| 接続・認証 | ミニアプリの入口・チャネル設定、本人確認、APIの利用権限、認証切れからの復帰。LINEの開発要件は公式資料で確認 |
| 表示 | 公式資料に基づく手順・リンク、結果確認の配置、数値の説明・時間の測定区間、選択肢回答の表示 |
| 入力・通信 | 入力長、タイムアウト、API利用量に対する必要最小限の制限、外部送信の説明、本文や秘密値を不用意に残さないログ |
| 状態の管理 | 履歴保存を増やさない一時保持・破棄、画面の寿命と認証の寿命の区別。複数画面の同期機能は追加せず、検証範囲を明記 |
| 確認方法 | 少数の実機確認例と、会話分岐・認証・失敗時の基本的な開発テスト |

正式なSpecへ進む際は[Specサイズ方針](.kiro/steering/spec-sizing.md)に従い、規模を判定してから要件・設計・タスクをレビューする。本書では単一Specか分割かを確定せず、実装を開始しない。
