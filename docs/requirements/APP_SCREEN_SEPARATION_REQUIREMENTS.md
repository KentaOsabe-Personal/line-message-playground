# アプリ画面分割 要件定義

## 文書情報

- 状態: 確定
- 確定日: 2026-08-29
- 対象: Frontendの画面分割、画面遷移、およびUI統一

## 1. 背景と目的

現在は、アカウント管理、チャネル管理、リッチメニュー管理、およびメッセージ配信が認証後の一画面に集約されている。

本対応では、各機能を独立した画面へ分割し、トップ画面と共通ナビゲーションから移動できる構成にする。既存機能の責務を整理し、アプリ全体のUIを統一する。新しい業務機能は追加しない。

## 2. 対象画面とURL

| 画面 | URL | 主な役割 |
|---|---|---|
| トップ画面 | `/liff` | 各機能画面への入口 |
| チャネル管理画面 | `/liff/channels` | LINEチャネルの登録・設定・状態管理 |
| アカウント管理画面 | `/liff/account` | ownerと配信先の連携管理 |
| リッチメニュー管理のチャネル選択画面 | `/liff/rich-menus` | 管理対象チャネルの選択 |
| チャネル別リッチメニュー管理画面 | `/liff/rich-menus/{channelId}` | 対象チャネルのリッチメニュー管理 |
| メッセージ配信画面 | `/liff/deliveries` | 既存のLINEテスト配信 |
| 404画面 | 上記以外 | 未定義URLの通知 |

### 2.1 URLとブラウザ遷移

1. ルートURL `/` は `/liff` へリダイレクトする。
2. `/` 以外の未定義URLは404画面を表示し、`/liff`へ一律リダイレクトしない。
3. 各画面は、再読み込み、URL直接アクセス、ブラウザの戻る・進むに対応する。
4. 未認証で保護対象URLへアクセスした場合は、そのURLでログインを要求し、認証成功後に要求時の画面を表示する。
5. 認証後の復帰先は、本書で定義した内部ルートだけを許可する。外部URLや任意URLは受け付けない。
6. 動的URLの`{channelId}`は登録済みチャネルの識別子として検証する。
7. 存在しない、またはownerが利用できない`{channelId}`は、どちらも同じ「対象が見つからない」表示にする。権限の有無を推測できる情報は出さない。
8. 前項の画面には、リッチメニュー管理のチャネル選択画面へ戻る導線を表示する。

## 3. Frontendルーティング

1. runtime依存として`react-router`を追加する。
2. Declarative modeの`BrowserRouter`を使用する。
3. 通常のパスURLを使い、hash routingや自作ルーターは使用しない。
4. 静的画面、`{channelId}`を持つ動的画面、および404画面を明示的にルート定義する。
5. 画面遷移用カードや画面内導線には`Link`を使用する。
6. 共通ヘッダーの機能ナビゲーションには`NavLink`を使用し、現在画面を表す状態を設定する。
7. 既存のAPI読込み責務は各Componentに維持する。React RouterのData modeまたはFramework modeへは移行しない。
8. ViteからngrokまでのFrontend配信経路は、定義済みの`/liff/...`へ直接アクセスしてもSPA entryを返すようにする。
9. LIFF Endpoint URLとLINEログインのredirect URIは`/liff`のまま維持する。

## 4. 共通レイアウトとナビゲーション

### 4.1 共通ヘッダー

認証後の通常画面には共通ヘッダーを表示する。

共通ヘッダーの構成:

- トップ画面へのリンクとなるアプリ名
- 4機能へのナビゲーション
- 認証中ownerの表示名
- ログアウト操作

機能ナビゲーションとトップ画面の機能カードは、次の順で統一する。

1. チャネル管理
2. アカウント管理
3. リッチメニュー管理
4. メッセージ配信

現在の機能画面は、視覚的にも支援技術からも判別できる状態にする。機能画面間はトップ画面を経由せず直接移動できる。

各画面は可視の`h1`を一つだけ持つ。ページ見出しには画面名だけを表示し、補足説明文は付けない。

### 4.2 トップ画面

トップ画面は、4機能を選ぶナビゲーション専用画面とする。

表示するもの:

- アプリ名
- 認証中ownerの表示名
- ログアウト操作
- 4機能へのカード

表示・実行しないもの:

- アプリ名直下の説明文
- チャネル件数、配信結果、警告状態などの機能データ
- 個別機能の管理操作や配信操作

各カードは、カード全体を操作できるボタン風の見た目にする。ただし、意味と実装は画面遷移用リンクとする。カードには機能名と遷移を示す視覚要素だけを表示し、説明文は付けない。タブやアコーディオンは使用しない。

## 5. 各機能画面の責務

### 5.1 チャネル管理

含める機能:

- 登録済みチャネル一覧
- 新規チャネル登録
- 表示情報と識別情報の編集
- アクセストークンとチャネルシークレットの設定・更新
- 接続確認
- 有効化、無効化、および必要な回復操作
- チャネル物理削除
- 対象チャネルのリッチメニュー管理画面への導線

含めない機能:

- リッチメニューの編集、適用、解除、および履歴表示
- 配信先の登録、状態変更、および連携解除
- メッセージ配信

### 5.2 アカウント管理

含める機能:

- ownerのLINE連携状態表示
- チャネルごとの配信先登録
- 配信先の有効化・無効化
- チャネル単位の連携解除
- ownerの全連携解除

含めない機能:

- LINEチャネルの登録、資格情報、状態変更、および削除
- リッチメニュー管理
- メッセージ配信
- ログアウト。ログアウトは共通ヘッダーで扱う

### 5.3 リッチメニュー管理

#### チャネル選択画面

1. トップ画面と共通ヘッダーの「リッチメニュー管理」は`/liff/rich-menus`へ遷移する。
2. 全登録済みチャネルを表示する。利用不可のチャネルも隠さず、状態と利用できない理由を示す。
3. 有効かつprovider ID設定済みのチャネルは、通常の管理画面へ進める。
4. 無効かつprovider ID設定済みのチャネルは、リッチメニュー実状態と適用履歴を読み取り専用で確認できる。
5. provider ID未設定のチャネルは選択不可とし、理由を表示する。
6. 無効化処理中など競合するライフサイクル処理がある場合は、現在状態を表示し、保存状態が許可する回復操作だけに制限する。
7. 登録済みチャネルが0件の場合は空状態を表示し、チャネル管理画面へのボタン風リンクを表示する。新規チャネル登録フォームは重複配置しない。

#### チャネル別管理画面

1. チャネル選択後は`/liff/rich-menus/{channelId}`を表示する。
2. チャネル管理画面の「リッチメニューを管理」も、対象チャネルの同じURLへ直接遷移する。
3. チャネル選択画面へ戻る導線を常に表示する。
4. チャネル選択画面から遷移した場合は、ブラウザの戻る操作でも選択画面へ戻れる。
5. provider ID未設定のURLへ直接アクセスした場合は、利用できない理由とチャネル管理画面へのボタン風リンクを表示し、管理操作は表示しない。

したがって、リッチメニュー管理への入口は次の複数導線を持つ。

- トップ画面からチャネル選択画面
- 共通ヘッダーからチャネル選択画面
- チャネル管理画面から対象チャネルの管理画面

### 5.4 メッセージ配信

トップ画面と共通ヘッダーでは「メッセージ配信」、画面見出しでは「LINEテスト配信」と表示する。

既存の次の機能だけを移す。

- 配信元チャネル1件の選択
- 登録済みrecipient 1件の選択
- 件名、本文、および受取確認の入力
- 送信前プレビュー
- 確認済み内容の送信
- 現在の送信操作の処理状態・結果表示
- 結果不明時の同一操作に対する状態再確認
- 完了後の新しい配信開始

次の新機能は追加しない。

- 複数recipientへの一括配信
- 配信予約
- 過去の配信履歴一覧
- 配信テンプレート
- 配信分析

## 6. 認証とアカウント状態

### 6.1 全連携解除中

1. 全連携解除が未完了の場合、どの画面URLへアクセスしても`/liff/account`へ移動する。
2. 同画面には全連携解除の回復画面だけを表示し、通常のアカウント管理機能は表示しない。
3. 4機能の共通ナビゲーションは表示しない。
4. 全連携解除の続行と状態再確認だけを許可する。
5. 完了後は未認証状態とし、再利用時はログインを要求する。

### 6.2 認証セッション失効

1. 現在の許可済み内部URLを維持し、ログイン要求を表示する。
2. 認証が必要な画面内容は直ちに非表示にする。
3. 未保存のフォーム入力とプレビューを破棄する。
4. 再ログイン後は同じ画面URLへ復帰し、Backendから最新状態を再取得する。
5. 失効前の送信、更新、削除などを自動再実行しない。

### 6.3 明示的ログアウト

1. 履歴を置換して`/liff`へ移動し、ログイン要求を表示する。
2. 未保存入力、プレビュー、認証後の復帰先、保持中の操作ID、およびowner別の一時キャッシュを消去する。
3. Backend受付済み処理は中断しない。
4. 履歴から以前の機能URLへ移動しても保護対象画面は表示しない。
5. 再ログイン後は以前の機能画面へ復帰せず、トップ画面から開始する。

## 7. 画面遷移と処理状態

### 7.1 未保存入力

1. 未保存内容があっても、画面離脱時の破棄確認は表示しない。
2. 共通ヘッダー、トップへの移動、画面内リンク、戻る・進む、再読み込み、およびタブを閉じる操作では、未保存内容を破棄する。
3. 破棄した内容を遷移後に復元しない。
4. 本要件は、既存の`LINE_RICH_MENU_REQUIREMENTS_INPUT.md`にある画面離脱時の入力破棄確認だけを置き換える。
5. 削除、送信、外部状態変更、および同一画面内で入力を消去する操作に対する既存確認は維持する。
6. 全連携解除、チャネル無効化・物理削除、リッチメニュー適用解除・管理終了、テンプレート変更時の入力消去、およびメッセージ送信前プレビューの確認は削除しない。

### 7.2 Backend受付後

1. メッセージ送信、リッチメニュー適用、チャネル更新などの受付後も、処理中の確認なしで別画面へ移動できる。
2. 画面移動を理由にBackend受付済み処理を中断または自動再送しない。
3. 元の画面へ戻った場合は、保存済みの最新状態と進行中操作を再取得する。
4. メッセージ配信では、不透明な操作IDだけを同一ブラウザセッション中に保持できる。
5. 入力本文、チャネル資格情報、リッチメニュー入力、およびプレビュー内容は、遷移をまたぐ復元目的でブラウザの永続領域へ保存しない。
6. 結果不明の操作は新規操作として自動再実行せず、同じ操作IDの状態確認だけを許可する。

## 8. データ読込み境界

1. 現在のURLに対応する機能画面だけをmountし、その機能に必要なAPIだけを呼び出す。
2. トップ画面では認証確認以外の機能APIを呼び出さない。
3. 表示中でない機能Componentを非表示状態でmountし続けない。
4. 画面離脱時は表示用リクエストを可能な範囲で中断する。中断できない場合は、後着した応答を画面状態へ反映しない。
5. Backend受付済みの更新、適用、および配信処理は画面離脱を理由に中断しない。
6. 画面へ再訪した場合はBackendから最新状態を取得する。

## 9. 読込み・エラー表示

1. 読込み中やエラー時も共通ヘッダーとページ見出しを維持する。
2. ページ内に統一した読込み状態またはエラー状態を表示し、空白画面や画面全体だけのspinnerにはしない。
3. 再試行して安全な取得処理にだけ再試行操作を表示する。
4. エラー中も利用可能な共通ナビゲーションを維持する。
5. 状態変化は支援技術へ通知する。

## 10. ページタイトルとフォーカス

| 画面 | `document.title` |
|---|---|
| トップ | `LINE Message Playground` |
| チャネル管理 | `チャネル管理 \| LINE Message Playground` |
| アカウント管理 | `アカウント管理 \| LINE Message Playground` |
| リッチメニュー管理のチャネル選択 | `リッチメニュー管理 \| LINE Message Playground` |
| チャネル別リッチメニュー管理 | `{チャネル名} \| リッチメニュー管理` |
| メッセージ配信 | `LINEテスト配信 \| LINE Message Playground` |
| 404 | `ページが見つかりません \| LINE Message Playground` |

画面遷移リンクによるルート変更後は、ページの`h1`へフォーカスを移す。同一画面内の再取得では移動しない。エラーは支援技術へ通知するが、入力中のフォーカスを奪わない。

## 11. UIデザイン

### 11.1 全体方針

新しいトップ画面や共通ヘッダーだけでなく、既存の全機能画面も同じデザイン体系へ揃える。既存ワークフロー、入力項目、操作、表示データは、本書で明示した変更を除き維持する。

視覚方針:

- 白、淡いグリーン、濃い文字色を基調とする
- ページ背景は薄いグレーグリーン
- カードは白背景、細い境界線、控えめな影
- LINEグリーンを主要操作とフォーカス表現に使用
- 赤は危険操作に限定
- 状態表示の色と表現を統一
- 文字、入力欄、ボタン、リンク、余白、角丸を全画面で統一
- 派手なgradient、強い影、不要なanimationは使用しない

機能追加に当たるボタンは増やさない。ただし、画面分割に必要なカード、共通ナビゲーション、戻る導線、空状態からの導線は追加できる。

### 11.2 Tailwind CSS

1. build依存としてTailwind CSSと`@tailwindcss/vite`を導入する。
2. CDN版は使用せず、Vite buildとlockfileで管理する。
3. 色、文字、余白、角丸、影、最大幅、breakpointをtheme variableとして定義する。
4. responsive、hover、focus、disabled、および状態表示はutility classで実装する。
5. Bootstrap、React-Bootstrap、その他のUI component libraryは導入しない。
6. 通常CSSは、複雑なリッチメニュー固有表現などutility classだけでは不適切な箇所に限定する。
7. 今回の対応で全画面を移行し、旧画面ごとの重複したbutton、panel、状態表示CSSを残さない。

### 11.3 Responsive

1. Desktop利用を主対象とする。
2. Desktopでは共通ナビゲーションを横並びにする。
3. 狭い画面では、機能ナビゲーション、現在状態、owner表示、およびログアウトを折り畳みメニューへ収める。
4. トップ画面のカードは広い画面で2列、狭い画面で1列とする。
5. ページ全体に不要な横scrollを発生させない。
6. SmartphoneとLINEアプリ内browserは正式な受入対象にせず、best effort対応とする。

### 11.4 Accessibility

WCAG 2.2 Level AAを設計目標とする。認証取得や第三者監査は対象外とする。

最低要件:

- 通常文字は4.5:1以上、大きな文字とUI境界は3:1以上のcontrast
- 色だけに依存しない状態表現
- keyboardだけで全操作が可能
- keyboard trapを発生させない
- 可視で隠れないfocus表示
- 原則24×24 CSS px以上のpointer target。ただしWCAGが認める例外を除く
- 適切なlabel、heading、landmark、現在状態、およびstatus通知

## 12. 対応browser

正式な対応範囲:

- Google Chrome 111以降
- Chromium版Microsoft Edge 111相当以降
- Safari 16.4以降
- Firefox 128以降

古いbrowser向けにTailwind CSS v3互換構成へ下げない。LINEアプリ内browserはbest effortとする。

## 13. Frontend・Backend境界

本対応はFrontendの画面構成、ルーティング、状態制御、およびUI整理を対象とする。

対象外:

- Backendの業務ロジック変更
- API schema変更
- Database変更やmigration
- 新規API endpoint

既存APIだけで確定要件を満たせないことが判明した場合は、Backend変更を暗黙に追加せず、実装を止めて別途判断する。

## 14. Testと受入条件

### 14.1 自動確認

既存のVitestとjsdomを使用し、新しいE2E test frameworkは導入しない。

最低限確認する項目:

- 全定義ルートの表示
- `/`から`/liff`へのリダイレクト
- 404表示
- 存在しない、または利用不可のchannel detail
- 未認証、session失効、明示的logout
- 全連携解除中の画面制御
- トップ画面の4カード
- 共通ヘッダー、直接遷移、現在画面表示
- ページタイトルとroute変更時のfocus
- リッチメニューの選択、詳細、戻る導線
- 現在画面だけが必要なAPIを呼ぶこと
- 画面離脱時に破棄確認を出さないこと
- Backend受付済み処理を自動再送しないこと
- 既存機能Componentの回帰

実装完了時に次を成功させる。

- `npm test`
- `npm run build`
- `git diff --check`

### 14.2 実browser確認

実browserでの見た目、操作感、および最終的なUI受入はuserが行う。Codexの完了条件には、実browserでの目視確認、pixel-perfect比較、および新規visual test frameworkの導入を含めない。

## 15. 対象外

- 本書にない新しい業務機能
- Backend変更
- Mobile-first設計
- LINEアプリ内browserの正式保証
- WCAG認証や第三者監査
- E2E・visual regression test frameworkの新規導入

## 16. 既存要件との優先関係

既存の機能要件は、本書と矛盾しない範囲で維持する。本書で明示した画面分割、ナビゲーション、UI統一、および画面離脱時の破棄確認に関する決定は、既存記述より優先する。
