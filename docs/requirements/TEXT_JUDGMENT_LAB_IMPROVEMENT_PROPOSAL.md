# 文章判定ラボ 改善案

作成：2026年9月27日／更新：2026年10月3日

本書は検討案であり、正式なspecの更新や実装の承認を兼ねない。現状はコードとspecから確認した。実APIでの精度・速度はまだ検証していない。

## 1. 目的と進め方

目的は、**Jevの組み込み方を理解・検証し、既存アプリで役立つ用途に採用すること**である。

まず用途を1つ選び、少数の試行で既存の操作と比べる。画面の改善では「判定が動作にどう使われたか」の説明を優先する。文章A・Bの比較画面は、繰り返し検証する必要があると分かってから追加する。

| 順序 | 取り組み | 判断できること |
| --- | --- | --- |
| 1 | 対象の操作と期待する利点を決め、既存の操作と手動で比較する | Jevを使う場面があり、入力や確認の負担を減らせるか |
| 2 | 判定・採用理由・次の動作と、質問の設計を見せる | Jevをどう組み込み、どの条件で本人に確認するか |
| 3 | 必要なら同じ文脈で文章A・Bを比較する画面を作る | 言い換えや否定による差を繰り返し調べられるか |

Jevが役立つかどうかも検証する。効果が小さければ既存の操作を維持する。数値のグラフ化は補助にとどめる。

## 2. 用途の選定と採用条件

### 対象操作を1つ選ぶ

最初の候補は、既存の通知相談で確認の負担を減らす用途とする。自由文から相談の種類・範囲・回避策を読み取り、確認を省く。ただし、通知相談を実際に使いたい場面があるかを先に確認する。

既存の管理機能に活用する場合は、自然文で操作の相談を受け、適切な機能画面と固定の手順を提示する案も候補とする。現在のナビゲーションより便利かを比較する。この案は現行ラボの範囲外なので、採用時に別途要件を定める。Jevの判定だけで配信や設定変更を実行する案は含めない。

試す前に「誰が、どの場面で、何を完了したいか」「現在の操作」「減らしたい負担」を短く記録し、対象を1つに絞る。

Choice・Score・Noulの学習と、実際の機能に使うかどうかの判断は分ける。用途に不要な判定を使うことは求めない。

### 比較画面を作る前に、少数の実API試行で確かめる

通知相談では、自由文で答える場合と選択肢で答える場合を、同じ開始条件・用件で試す。回答の確定内容と終了条件が同じになった試行で、時間や確認回数を比較する。そこまで進めなかった試行も、失敗ややり直しとして記録する。

| 記録すること | 確かめること |
| --- | --- |
| 入力、開始条件、期待する回答・動作、実際の結果 | 正しく完了できたか、何を誤って確定したか |
| 完了までの時間、確認回数、やり直し | 質問の削減が利用者の負担軽減につながったか |
| API待ち時間、呼び出し数、入出力トークン数 | 待ち時間と利用量が利点に見合うか |
| モデル、判定質問・採用規則の版 | どの条件で得た結果か |

最初は手動の検証メモでよい。現在の公開結果に含まれない利用量は、秘密情報を含めずに取得する方法を検証時に決める。取得できなければ未測定とし、呼び出し数だけで費用を判断しない。

採用条件として、同じ目的を達成でき、入力や確認の負担が減ることを提案する。誤った回答の確定、やり直し、待ち時間、利用量も許容範囲に収まることを条件とする。

許容する時間・利用量と、許容できない誤動作は、対象の操作を選んだ時点で決める。条件を満たさなければ質問の設計や用途を見直す。少数の試行から一般的な精度・高速性・費用対効果を断定しない。

## 3. 現状の仕組みと限界

自由文や例文を送ると、Choiceの7項目、Scoreの1項目、Noulの1項目を1回のAPI呼び出しで評価する。文脈として、現在の文章、直前の質問、確定済み回答、支障の状態、直近2件の受理済み発言を渡す。Backendが判定値を検証・正規化し、Frontendが会話に適用する。

選択肢の回答はJevを呼ばずに確定する。質問や案内は固定文で、確定済み回答は後の判定で上書きしない。

Scoreは、通知が届かない相談で回避策を確認するかどうかに使う。設定方法の相談や、回避策が回答済みの場合には、その確認を追加しない。Noulは急ぎの確認と詳しい手順の開閉に使う。案内内容や対応速度を変えるものではない。

現在の画面では、数値と動作の関係、発言時の文脈、検証すべき違いが分かりにくい。新しい相談を始めると前の表示が消えるため、同じ条件での比較もしにくい。毎回9項目を判定しても、すべてが動作に使われるわけではない。

## 4. 優先する改善は、判定と動作の関係を見せること

### 通常表示は3点に絞る

1. 今回確定したこと。文章から新たに採用した回答を示す。
2. 会話への影響。確認が不要になった項目、次の質問・案内、表示方法を示す。
3. 確認が必要なこと。情報が足りないか採用条件を満たさず、本人に聞く項目を示す。

次は、想定した判定が採用された場合の表示例であり、実測結果ではない。

> 入力：全部のトークで通知が来ません。LINEを開けば読めます。急いでいます。  
> 結果：すべてのトークで通知が届かず、LINEを開けば読めることを確定しました。範囲と回避策を聞き直さず、全体の通知設定の案内へ進みました。急ぎの要望に合わせて要点を先に表示しました。

この例で回避策の確認を省く直接の理由は、すでに回答を得たことである。Scoreだけの効果と説明しない。

選択肢には「Jev呼び出しなし」と表示する。判定が曖昧だった場合と、通信に失敗した場合も区別する。

### 詳細では、採用理由と質問の設計を見せる

「Jevの出力」「アプリの採用判断」「実際の動作」を分けて示す。理由の説明では、次の状況を区別する。

- 文章で言及されていない。
- 採用条件を満たさない。
- 確定済み回答を維持した。
- 対象外などの規則を優先した。
- 今の場面では使わない。
- 採用しても動作が変わらない。

理由の説明は、実際に適用した規則から作る。Jevの内部の思考や、応答にない根拠箇所を推測で生成しない。

数値と併せて、代表的な判定に渡した文脈`state`、質問`instructions`、候補・段階の定義`criteria`を読めるようにする。初期段階では質問や閾値を編集する機能は設けない。

| 判定 | 学ぶこと | 現在の採用条件 |
| --- | --- | --- |
| Choice | 候補から選ぶ。confidenceは候補確率の分布から計算され、正答率ではない | confidence・最大候補確率がともに0.70以上で最大候補が一意。`unclear`は要確認、`unmentioned`は未言及 |
| Score | 定義した段階番号の確率加重平均。現在は0＝支障なし、1＝不便だが目的を達成できる、2＝目的を達成できない | Choiceの「支障の根拠あり」が採用可能で、Scoreのconfidenceが0.70以上なら採用。1.5以上を支障大、それ未満を支障小とし、条件を満たさなければ要確認 |
| Noul | 「急ぎの要望があるか」のyesの確率。急ぎの強さではない | 0.80以上で急ぎ、0.20以下で急ぎなし、中間は要確認。未確定なら急ぎを質問する |

これらの閾値はアプリの初期方針で、正答を保証しない。数値の意味は[Choice](https://docs.typesafe.ai/primitives/choice)、[Score](https://docs.typesafe.ai/primitives/score)、[Noul](https://docs.typesafe.ai/primitives/noul)の公式仕様に基づく。複数質問は1回にまとめても追加のトークンを消費する。

各発言に、入力前の会話状態、送信した文脈、応答、適用結果を関連付ける。後の状態から説明を再計算しない。通常は直前の質問と主な変化を表示し、詳細を開くと文脈全体と数値を確認できるようにする。データはページ内のメモリだけに保持する。

## 5. 検証テーマと例文

テーマは例文と観察ポイントを選ぶために使い、判定質問や会話規則は変更しない。次の表には期待する違いを示す。実測結果ではない。各組で、前提となる相談と質問をそろえる。

| テーマ | 比較する文章・条件 | 観察すること |
| --- | --- | --- |
| 情報量 | 「通知が届きません」／「すべてのトークで通知が届きません。LINEを開けば読めます」 | 複数回答を読み取り、確認を省けるか |
| 言い換え | 「すべてのトークで通知が届きません」／「誰から連絡が来ても通知が出ません」 | 同じ種類・範囲になるか |
| 否定 | 通知不達の相談で「LINEを開けば読めます」／「LINEを開いても読めません」 | 回避策を区別し、後者では未解決終了・公式ヘルプ案内へ進むか |
| 急ぎ | 同じ設定相談に「急いでいません」／「今すぐ教えてください」を付ける | 案内の種類を保ち、Noulと手順の開閉が変わるか |
| 支障と急ぎ | 同じ通知不達の相談で急ぎなしを固定し、「家族に聞いて確認できるので支障は小さい」／「必要な連絡を確認できず予定を決められない」 | Scoreと急ぎを分けられるか。回避策のChoiceへの影響も確認する |
| 不明と曖昧さ | 範囲の質問に「範囲は分かりません」／「うーん、どうだろう」 | 本人の「分からない」と判定要確認を区別できるか |
| 対象外 | 「LINEの通知設定を知りたい」／「LINEのアカウントを削除したい」 | 対象内の案内と対応範囲の説明を分けられるか |

支障の記述は回避策のChoiceにも影響し得るため、Scoreだけの効果と決めつけない。実APIでは意味の読み取りを確認し、閾値だけを変えた分岐の検証には固定応答を使う。

## 6. 必要になってから追加するA・B比較画面

同じ用件を既存の操作と比べることで実用性を確かめる。文章A・Bの比較では、読み取りの違いを確かめる。

元の入力前の会話状態を固定し、A・Bには同じ質問、確定済み回答、支障の状態、直近発言を渡す。モデル、判定質問、採用規則もそろえる。Aの結果をBの文脈へ混ぜない。同じ条件でも、同じ結果になるとは保証しない。

画面には入力、期待した判定と実際の判定、採用した回答、次の動作、呼び出し数、待ち時間を並べる。数値だけが変わり動作が同じ場合も理由を示す。A・Bのどちらかが通信に失敗しても、判定の優劣として扱わない。

通常の相談と同じ状態遷移処理で、適用後の動作を確かめる。結果を通常の相談へ自動適用せず、回答の巻き戻しや過去の状態からの再開は追加しない。

比較はページ内の1組に限り、利用者の操作で順に評価する。Bは編集して再評価できる。同じ条件で評価に成功したAは再利用できる。小画面ではA・Bを縦に並べ、違いの要約を先に示す。

比較を閉じる、新しい相談を始める、ページを再読み込みする、のいずれかで比較データを破棄する。既存の同時実行・利用量・タイムアウトの制限を守る。大量の自動評価、永続的な履歴と復元、別のキーワード判定器は追加しない。

## 7. 検証と実装への引き継ぎ

画面の完成条件は、何を読み取り、なぜ採用・不採用となり、次に何が起きたかを発言ごとに説明できることとする。質問の設計も確認でき、確認の省略や追加、動作が変わらない場合、判定要確認、通信失敗を区別できることを求める。実用に採用するかは、2節の比較結果で別途判断する。

自動テストでは、説明と状態遷移が一致することを確認する。対象は通常の分岐、対象外、訂正、複数相談、確定済み回答、Score不採用、閾値の前後とする。表示用に丸めた数値を判定に使わず、後の操作で過去の説明が変わらないことも検証する。

比較機能を追加する場合は、A・Bの開始条件が一致すること、結果や遅れて届いた応答がもう一方に混ざらないこと、比較データが決めたとおりに破棄されることを確認する。

判定の正規化はBackend、会話への適用はFrontendの状態遷移で扱う。Controllerでは発言の記録と通信の寿命を管理する。説明のために画面へ分岐規則を複製しない。APIに理由や利用量などを追加する場合は、Backend・FrontendのDTO検証・共有fixtureを合わせて更新する。

学習面の改善は、既存の[要件](.kiro/specs/text-judgment-lab/requirements.md)のRequirement 12をもとに進める。[設計](.kiro/specs/text-judgment-lab/design.md)や[用語集](CONTEXT.md)と矛盾しないようにする。

正式なspecにする際は用途と変更範囲を決め、[Specサイズ方針](.kiro/steering/spec-sizing.md)に従って既存specの更新か新しいspecの追加かを選ぶ。用語や長期的な判断を確定したらCONTEXT.md・ADRへ記録する。Requirements、Design、Tasks、Implementationの順に人間の承認を得る。
