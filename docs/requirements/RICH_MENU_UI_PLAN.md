# リッチメニュー詳細画面の改善計画

作成日: 2026-10-14  
状態: UI案作成用の計画。正式な要件・設計・実装の承認前。

## 1. 目的

リッチメニュー詳細画面を「現在のメニューを確認し、必要なら変更する」画面へ整理する。

現在は適用済みのリッチメニュー画像が表示されず、何が設定されているか直感的に分からない。一方で、状態一覧や操作履歴が画面の多くを占めている。適用済み画像を中心に表示し、判断や操作に必要な情報へ絞る。

この文書は、まずFigmaでUI案を作成し、その案をもとに既存仕様の差分を確定するために使う。API名やコンポーネント名は実装候補であり、画面には表示しない。

## 2. 対象と前提

- 対象利用者は、自分のLINE公式アカウントを管理する認証済みowner。
- 対象画面は `/liff/rich-menus/{channelId}` のチャネル別リッチメニュー詳細画面。
- 今回の画像表示は、このアプリで適用したチャネル既定リッチメニューを対象とする。
- 利用者別メニューが設定されている場合は、チャネル既定リッチメニューよりも利用者別メニューが優先される。プレビューは個々の利用者の端末表示を保証するものではない。
- アプリ外で設定されたメニューは内容取得の対象に含めず、存在とLINE側での確認を案内する。
- 既存の共通ナビゲーション、テーマ、チャネル選択画面への戻る導線を利用する。
- 操作履歴の画面表示は撤去するが、Backendの記録と回復処理は維持する。

## 3. Figmaで作成するUIの方針

### 情報の優先順位

1. どのチャネルの画面か。
2. 現在どのリッチメニューが設定されているか。
3. 編集・解除など、次に何ができるか。
4. 問題がある場合、何を確認・操作すればよいか。

通常時は、チャネル名、現在の画像、編集・解除・更新の操作を中心にする。状態の説明や警告を常設して画面を埋めない。

### 通常時の画面構成

上から次の順序とする。

1. チャネル選択画面へ戻るリンク。
2. チャネル名と短い状態表示。
3. 「現在のメニュー」の画像。
4. 主操作の「編集する」と、補助操作の「適用解除」「更新」。
5. 既存の「チャネルの停止・削除」の折りたたみ。

画像は元の縦横比を保って全体を表示する。切り抜きや引き伸ばしを行わず、コンパクト型とラージ型の両方に対応する。

画像の下に設定情報を常時列挙しない。表示名と完全なリンク先の確認・変更は編集時に行う。

### 編集時の画面構成

- 「編集する」を押したときに、同じ詳細画面内で編集フォームを表示する。
- 現在のテンプレートと全項目の表示名・リンク先を初期入力する。
- 未設定の場合は「メニューを作成」から開始する。
- 編集フォームには「変更内容をプレビュー」と「キャンセル」を配置する。
- 生成後の画像は「変更内容のプレビュー」と明示し、「現在のメニュー」と区別する。
- 適用前に、対象チャネル、画像、全項目の表示名・リンク先、置換による影響を確認できるようにする。
- 「LINEに反映」で適用する。編集しただけ、またはプレビューを生成しただけでは現在の設定を変更しない。
- キャンセル時は未適用の入力と確認用プレビューを破棄し、現在のメニュー表示へ戻る。
- 古いテンプレート版などで編集を開始できない場合は、自動的に別の版へ置き換えず、作り直しが必要なことを案内する。

現在のメニューと編集中の内容は別の情報として扱う。編集開始時に現在の画像を小さく残すか、折りたたむかは、Figmaで視認性を比較して決める。

### 表示を整理する要素

| 現在の要素 | 改善後 |
| --- | --- |
| LINE状態・管理対象有無・履歴件数の概要 | 重複を撤去し、短い状態表示へ集約 |
| 保存状態・提供モード・操作状態・後片付けの一覧 | 常設を撤去し、必要な状態だけ案内 |
| 操作履歴と件数 | 詳細画面から撤去 |
| 実行可能な操作の説明一覧 | 実際に利用できるボタンで表現 |
| 通常時にも表示される「対応が必要です」 | 確認や回復が必要な場合だけ表示 |
| 操作ID・内部状態名 | 通常の画面表示から外す |
| 操作結果 | 直前の操作結果を短く表示し、重複表示を避ける |
| チャネル停止・削除 | 今回は既存の折りたたみ内に維持 |

### 見た目と操作性

- 既存アプリの配色、余白、角丸、文字サイズ、フォーカス表現を基準にする。
- 主操作を明確にし、解除などの破壊的操作を同じ強さで並べない。
- 補助操作は狭い画面でも押せる配置にし、横スクロールを必要としない。
- 成功、処理中、失敗、確認待ちは色だけに依存せず文章で区別する。
- 長いチャネル名・URL、日本語の長い表示名でもレイアウトが崩れないようにする。
- 画像には内容を識別できる代替テキストを設ける。
- キーボード操作時のフォーカスと、編集開始・キャンセル後の移動先を考慮する。
- ライト・ダーク両方で視認性を保つ。

## 4. Figmaで用意する画面状態

| 状態 | 表示内容 | 主な操作・制約 |
| --- | --- | --- |
| 適用済み・正常 | 現在の画像と短い「適用中」表示 | 編集、適用解除、更新 |
| 未設定 | 「リッチメニューが設定されていません」 | メニューを作成、更新 |
| 読み込み中 | 画像領域の読み込み表示 | 以前の画像を最新として扱わない |
| 画像取得失敗 | 「画像を取得できませんでした」 | 画像の再取得。画面全体をエラーにしない |
| アプリ外のメニュー | アプリ外で設定されていることと確認先の案内 | LINE側で確認。外部メニューの編集・削除は提供しない |
| 外部変更・状態不一致 | 現在の設定を再確認する短い案内 | 許可された再取得・回復操作のみ表示 |
| 編集中 | 現在の設定が入力されたフォーム | プレビュー、キャンセル |
| 変更内容の確認中 | 未適用と分かる画像、全項目のリンク先 | LINEに反映、編集へ戻る |
| 確認用プレビュー期限切れ | 入力を残し、再生成が必要と案内 | プレビューを再生成 |
| 適用・解除の処理中 | 実行中の操作を短く表示 | 連打と競合操作を禁止 |
| 操作結果が不明 | 「前回の操作結果を確認してください」 | 同じ操作の結果を確認。新規適用を禁止 |
| 後片付けが必要 | 残った資源と必要な処理を簡潔に案内 | 許可された対象の後片付け |
| チャネル停止中 | 停止中であることと保存済み情報 | 読取専用。LINEの現在画像を確認済みとして表示しない |

アプリ外・結果不明・状態不一致の場合に、保存済みの古い画像を「現在のメニュー」として代わりに表示しない。画像取得失敗とメニュー未設定も区別する。

無効化確認中や操作禁止の状態では、一覧を省略しても「操作できない理由」と「次に行うこと」は残す。操作可否はBackendが返す許可状態に従う。

## 5. 操作の流れ

### 現在の内容を確認する

1. チャネル別詳細画面を開く。
2. 現在の既定メニューを確認し、表示可能な画像を取得する。
3. 画像と短い状態表示で現在の内容を確認する。

### 内容を変更する

1. 「編集する」を押す。
2. 現在の設定をもとに表示名・リンク先などを変更する。
3. 「変更内容をプレビュー」を押す。
4. 画像と全リンク先、対象チャネル、必要な置換警告を確認する。
5. 「LINEに反映」を押す。
6. 適用結果が確定したら現在のメニューを再取得する。

### 適用を解除する

1. 「適用解除」を押す。
2. 対象と解除の影響を確認する。
3. 解除を確定する。
4. 完了後に状態を再取得する。解除後の表示は取得結果に従い、常に未設定になるとは決めつけない。

適用・解除が結果不明になった場合は成功表示へ進めず、同じ操作を確認する導線へ切り替える。

## 6. 実装計画

### 6.1 既存仕様の差分整理

- `line-rich-menu-foundation`に、適用済み画像と設定の閲覧契約を追加する。
- `line-rich-menu-admin-lifecycle`に、現在の画像を中心とする画面構成、編集開始、履歴表示の撤去を反映する。
- `app-screen-separation`との接点を確認し、既存の画面遷移・認証・画面離脱の契約を維持する。
- 用語は「現在のメニュー」と「変更内容のプレビュー」を区別する。既存の「リッチメニュープレビュー」は適用前の確認を意味するため、必要な用語・共通文書の更新を行う。

### 6.2 Backendの閲覧処理

- 現在の既定メニューと管理対象の一致を確認し、画像と保存済み設定を取得する閲覧APIを追加する。
- 既存のLINE画像取得処理は検証情報だけを返しているため、表示用画像本体を返す取得経路を設ける。
- owner・provider・対象チャネルのアクセス制御を行い、外部通信後にも対象とrevisionを再検証する。
- 現在の資源と適用時の設定を対応付け、履歴の先頭を現在の設定と推測して利用しない。
- 取得中の設定変更、画像不在、取得失敗を安全に区別する。
- 閲覧のために適用前の確認トークンを発行したり、LINEの設定を変更したりしない。
- 画像の履歴保存や新しい永続化基盤は追加しない方針とする。DB migrationの要否は設計時に確定する。

### 6.3 Frontendの表示・状態管理

- 現在のメニュー表示を専用コンポーネントとして追加する。
- 閲覧APIに対応する通信、DTO検証、状態遷移を既存の責務分離に沿って追加する。
- 適用済み画像と適用前プレビューを別の状態として保持する。適用済み画像には10分間の有効期限を付けない。
- 編集開始時に現在の設定を初期入力する。
- 履歴コンポーネントの表示と、詳細画面初期表示時の履歴一覧取得を除去する。回復や削除確認に必要な状態情報は維持する。
- 画像取得の失敗を、チャネル状態取得の失敗から分離する。
- 適用・解除後に現在の画像と状態を更新する。
- チャネル変更・画面離脱・認証失効時は表示情報と画像URLを破棄し、後着応答で古い画像を表示しない。

主な変更候補は次のとおり。

- `frontend/src/RichMenuAdminConsole.tsx`
- `frontend/src/RichMenuStatePanel.tsx`
- `frontend/src/RichMenuRecoveryPanel.tsx`
- `frontend/src/RichMenuEditor.tsx`
- `frontend/src/RichMenuPreview.tsx`
- `frontend/src/richMenuAdminApi.ts`
- `frontend/src/richMenuAdminDto.ts`
- `frontend/src/richMenuAdminState.ts`
- `backend/linerichmenus/`の閲覧API、service、gateway、presenter、および関連する型・repository

### 6.4 検証

- 適用済み・未設定・外部変更・停止中・画像取得失敗の表示を確認する。
- 既存の適用済みメニューが、再適用せずに表示できることを確認する。
- 編集途中の内容が現在の画像へ混ざらないことを確認する。
- 適用・解除後の更新、チャネル切替時の後着応答、認証失効時の消去を検証する。
- 結果不明時の再確認、後片付け、二重実行防止、操作禁止条件を回帰テストする。
- Backendの閲覧認可と、画像取得中の設定変更を検証する。
- 詳細画面で不要な履歴一覧リクエストが発生しないことを確認する。
- Frontend／Backendの品質チェックと関連テストを実行する。
- 狭い画面、キーボード操作、ライト・ダーク配色を目視確認する。

## 7. 規模と進め方

- 変更分の見積もりは、テスト・統合を含む8〜11実行タスク程度。1タスクは1〜3時間を想定する。
- 責任境界は、Backendの適用済み情報参照、Frontendの画面・状態管理、統合検証。
- 成果は「現在のメニューを直感的に確認・変更できる詳細画面」の一つ。
- 新しい適用・解除の状態機械や補償フローは追加せず、既存契約を再利用する。
- 変更分のサイズ判定は `PASS (single-spec)` 相当。既存spec全体の再見積もりではなく、正式な要件・設計・タスク確定前に再評価する。

進行順は、FigmaでUI案作成、UI方針の合意、既存仕様の要件更新、設計、タスク、実装とする。各段階の承認はプロジェクトのKiroワークフローに従う。

## 8. Figma成果物の確認ポイント

- 詳細画面を開いた直後に、対象チャネルと現在のメニューが分かる。
- 正常時に、状態一覧・履歴件数・操作履歴が表示されない。
- 編集開始、プレビュー、適用、キャンセルの流れが分かる。
- 現在の画像と未適用の画像を取り違えない。
- エラーや確認待ちでは、必要な案内と次の操作が見つかる。
- コンパクト型・ラージ型の画像が全体表示される。
- デスクトップ幅と狭い画面幅の両方で操作できる。
- 主操作、補助操作、解除操作の優先度が見た目で分かる。

UI案では、通常時、未設定、編集中、変更内容の確認中、画像取得失敗、結果不明の状態を優先して作成する。その他の状態はコンポーネントのバリエーションとして整理する。
